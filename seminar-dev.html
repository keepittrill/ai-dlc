WHERE IT PAYS

승인 게이트의 가치는 “틀린 코드를 잡는 것”이 아니라 틀린 방향의 하위 작업을 아예 발생시키지 않는 것입니다. 1장의 사고는 게이트 하나로 막혔을 일입니다.

정확히 하기

“AI-DLC는 Agile을 대체한다?”

논문은 양쪽을 다 말합니다. Principle 1은 “retrofit이 아니라 reimagine — 더 빠른 마차가 아니라 자동차가 필요하다”며 재구성을 선언합니다. 그러나 Section VI(Adoption)은 “AI-DLC does not deviate much from the existing Agile methods”라며 하루 안에 익힐 수 있게 설계했다고 밝힙니다. Principle 7은 Sprint를 Bolt로 “의도적으로 개명”한 것이라고 설명합니다.

정확한 표현은 “AI-DLC는 Agile·DevSecOps를 대체하는 것이 아니라, 그 위에서 AI와 사람의 실행 방식을 재구성한다”입니다. 반복·사용자 스토리·리스크 레지스터는 그대로 남습니다(Principle 6).

03 / 17:00–25:00 · BROWNFIELD ENTRY

SECTION V · BROWN-FIELD DEVELOPMENT

기존 시스템에서는
코드를 먼저 모델로 승격시킵니다.

논문이 Greenfield와 다르게 규정한 단계는 딱 하나입니다 — Construction 시작 전에 “코드를 의미가 풍부한 모델링 표현으로 승격(elevate)”합니다. 컨텍스트를 간결하고 정확하게 만들기 위해서입니다. 이유는 실무적입니다.

❌ 저장소를 통째로 던진다

“이 레포 보고 환불정책 바꿔줘”

파일 1,400개 · 컨텍스트 초과 · AI가 호출되지 않는 죽은 코드와 살아 있는 경로를 구분하지 못합니다. 영향 분석이 통째로 틀립니다.

✅ 정적 · 동적 모델로 승격

2장의 문서로 압축한다

정적 모델 — 컴포넌트, 책임, 관계.

사람과 PM이 역공학 결과를 검증한 뒤에야 다음으로 갑니다.

이 두 문서가 세미나에서 실제로 한 일

Brownfield에서 AI에게 저장소 전체를 주는 것과 이 두 장을 주는 것의 차이가, 뒤의 영향 분석 정확도를 결정합니다.

AI의 역질문 · 8

각 질문을 눌러 결정과 그 결정이 코드에 남는 방식을 확인하세요.

프롬프트를 길게 쓰는 능력이 아니라, 이 여덟 개를 알아보고 답하는 능력이 개인 역량입니다.

  1. 결정 — 배송 완료일. 단, 정책 선택은 주문일 기준(아래 Q3과 짝).

    코드에 남는 방식 — 두 시각이 서로 다른 역할이므로 파라미터 이름으로 분리합니다. decide(order, policy, requestedAt)는 마감 계산에 order.deliveredAt()만, 정책 조회는 order.orderedAt()만 씁니다.

  2. 결정 — 판매 국가(관할) 시간의 그날 23:59:59.999까지.

    코드에 남는 방식 — Jurisdiction enum이 ZoneId를 들고 있게 하고, 계산을 Instant 산술이 아니라 LocalDate.plusDays().atTime(MAX).atZone()으로 바꿉니다. 그리고 KST/CET 경계 테스트를 인수 기준에 명시합니다.

  3. 결정 — 주문 시점에 유효했던 정책. 소급 적용하지 않습니다.

    코드에 남는 방식 — 리포지토리 메서드 시그니처 자체에 박습니다. resolveAsOf(jurisdiction, category, orderedAt) — “as of”가 없으면 컴파일이 안 되게. 주석은 지워지지만 시그니처는 안 지워집니다.

  4. 결정 — LEGACY 정책(전역 7일)으로 폴백하고 경보를 올립니다. 고객 대면 기능이라 실패시키지 않되, 조용히 넘어가지도 않습니다.

    코드에 남는 방식 — 마이그레이션에서 모든 (관할 × 상품군) 조합에 LEGACY 행을 미리 적재해 폴백 경로가 실제로 데이터로 존재하게 만듭니다. 폴백 발생 시 refund.policy.fallback 카운터 증가 → 알람.

  5. 결정 — TTL 만료를 기다리지 않습니다. 캐시 키에 정책 epoch를 포함시켜 세대 교체 방식으로 무효화합니다.

    코드에 남는 방식 — refundPolicy:v{epoch}:{KR}:{ELECTRONICS}. 정책 변경 트랜잭션이 epoch를 증가시키면 이전 키는 아무도 안 읽고 TTL로 자연 소멸합니다. Redis KEYS/SCAN 기반 대량 삭제가 필요 없습니다.

  6. 결정 — optional 필드만 추가. 기존 required 집합은 건드리지 않습니다.

    주의 — “필드 추가는 안전하다”는 가정입니다. 구형 모바일 클라이언트가 strict 파서를 쓰면 unknown 필드나 unknown enum에서 터집니다. 이 가정을 계약 테스트로 증명하기 전까지는 결정이 아닙니다. (7장에서 실제로 실패합니다)

  7. 결정 — 정책 행은 수정하지 않고 append합니다. 기존 행에 effective_to를 닫고 새 행을 여는 것을 한 트랜잭션에서 처리합니다.

    코드에 남는 방식 — DB의 배제 제약(EXCLUDE USING gist)으로 같은 관할·상품군의 유효 기간이 겹치는 것을 물리적으로 불가능하게 만듭니다. 애플리케이션 검증에 의존하지 않습니다.

  8. 결정 — 이미 고객에게 통보된 판정은 뒤집지 않습니다. 판정 결과를 refund_decision 테이블에 policy_version과 함께 기록하고, 롤백 시에도 그 판정은 유효한 것으로 처리합니다.

    왜 중요한가 — 롤백을 코드만 되돌리는 것으로 생각하면, 이미 “환불 가능합니다”라고 안내받은 고객이 다음 날 거절됩니다. 롤백 계획은 데이터 계획입니다.

여덟 개 중 Q2·Q6·Q8은 “구현이 아니라 결정”입니다. AI는 이걸 물을 수 있지만 답할 수는 없습니다 — 답은 사업·법무·운영의 맥락에서 나옵니다.

public final class RefundPolicyEvaluator {

    public RefundDecision decide(Order order, RefundPolicy policy, Instant requestedAt) {
        ZoneId zone = policy.jurisdiction().zoneId();

        // 절대시각 산술이 아니라 관할의 달력 날짜로 계산한다 (Q2)
        Instant deadline = order.deliveredAt()
                .atZone(zone).toLocalDate()
                .plusDays(policy.returnWindowDays())
                .atTime(LocalTime.MAX)
                .atZone(zone).toInstant();

        boolean eligible = !requestedAt.isAfter(deadline);

        return new RefundDecision(eligible, deadline,
                eligible ? ReasonCode.WITHIN_RETURN_WINDOW : ReasonCode.OUTSIDE_RETURN_WINDOW,
                policy.version());
    }
}

왜 이 형태인가: 파라미터가 전부 값이고 필드가 없습니다. Clock도 주입하지 않고 requestedAt을 받습니다. 그래서 어떤 시간대·어떤 순간이든 테스트가 3줄이고, 1장의 사고를 재현하는 테스트를 즉시 쓸 수 있습니다.

# ADR-011 · 정책 판정과 LLM 설명의 분리

## Decision
LLM은 환불 가능 여부를 결정하지 않는다.
RefundDecision을 입력으로 받아 설명 문장만 생성한다.

## Consequences
+ 모델 교체·프롬프트 변경이 판정에 영향을 주지 않는다
+ 판정은 결정론적으로 테스트 가능하다
+ LLM 장애가 기능 장애가 아니라 문구 저하로 격리된다
− 설명이 판정과 모순될 가능성은 별도 평가가 필요하다

HOW TO ADD A CASE

사례 하나 = 8칸. 코드 수정은 이 블록 하나입니다.

  1. ① 사고를 고른다

    “테스트는 통과했는데 운영에서 틀린” 사건이 최고입니다. 5xx 장애는 오히려 약합니다 — 이미 알람이 잡으니까요.

  2. ② 질문 8개를 역산한다

    사후에 “이걸 미리 물었다면 막혔다”를 세어보면 대개 6~10개가 나옵니다. 그게 Inception 화면이 됩니다.

  3. ③ diff를 10줄로 줄인다

    슬라이드 한 장에 안 들어가면 사례가 아니라 코드 리뷰입니다.

  4. ④ 실패한 증거를 하나 남긴다

    전부 통과한 검증 화면은 아무도 안 믿습니다.

  5. ⑤ 2차 변경을 측정한다

    파일 수 비교가 설계 개선의 유일한 정량 증거입니다.

APPENDIX A · THE ACTUAL PROMPTS FROM THE PAPER

논문 부록에 실린
실제 프롬프트입니다.

AI-DLC의 승인 게이트는 추상적인 원칙이 아니라 프롬프트에 박힌 문장입니다. 아래는 논문 Appendix A의 구조를 그대로 옮긴 것으로, 복사해서 오늘 바로 쓸 수 있습니다.

SETUP
We will work on building an application today. For every front end and backend
component we will create a project folder. All documents will reside in the
aidlc-docs folder. Throughout our session I'll ask you to plan your work ahead
and create an md file for the plan. You may work only after I approve said plan.
These plans will always be stored in aidlc-docs/plans folder.
Requirement / feature change documents → aidlc-docs/requirements
User stories → aidlc-docs/story-artifacts
Architecture and design documents → aidlc-docs/design-artifacts
All prompts in order → aidlc-docs/prompts.md
Confirm your understanding of this prompt. Create the necessary folders and
files for storage, if they do not exist already.
THE GATE SENTENCE · 논문에서 반복되는 문장
Your Role: You are an experienced software engineer. Before you start the task
as mentioned below, please do the planning and write your steps in an md file
with checkboxes against each step in the plan. If any step needs my clarification,
please add it to the step to interact with me and get my confirmation. Do not
make critical decisions on your own. Once you produce the plan, ask for my
review and approval. After my approval, you can go ahead to execute the same
plan one step at a time. Once you finish each step, mark the checkboxes as
done in the plan.
BROWNFIELD · 코드 승격 (오늘의 3장)
Your Task: Elevate the existing code under refund/ into a higher-level
modelling representation. Produce two documents:
  (1) static model  — components, descriptions, responsibilities, relationships
  (2) dynamic model — how the components interact to realize the most
                      significant use cases
Do not modify any source code. Write both into aidlc-docs/design-artifacts/.
List every assumption you had to make, and mark the ones you could not verify
from the code alone.
부록에서 실무자가 가져갈 한 가지

세 프롬프트에 공통으로 들어간 문장은 “Do not make critical decisions on your own”과 “ask for my review and approval”입니다. AI-DLC의 승인 게이트는 도구가 아니라 이 두 문장입니다 — CLAUDE.md, .cursorrules, AGENTS.md 어디에 넣어도 오늘 작동합니다.

마지막 프롬프트의 “mark the ones you could not verify from the code alone”이 특히 중요합니다. AI가 확신하는 것과 확인한 것을 스스로 분리해 보고하게 만드는 한 줄입니다.
