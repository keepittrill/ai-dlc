04 / INSIDE AI-DLC

A METHODOLOGY YOU INSTALL, NOT READ

AI-DLC는 읽는 방법론이 아니라
설치하는 방법론입니다.

AWS가 실제로 공개한 것은 책이 아니라 실행 가능한 규칙 파일 묶음(awslabs/aidlc-workflows)입니다. 프로젝트에 복사하고 “Using AI-DLC”로 대화를 시작하는 순간, 에이전트가 절차를 따르기 시작합니다. Agile은 사람이 책을 읽고 행동을 바꿔야 했지만, AI-DLC는 방법론이 처음으로 코드처럼 배포 가능해진 사례입니다.

❌ AI-Managed

“통째로 만들어줘” — 에이전트가 멋대로 결정해 일관성이 깨지고 유지보수 폭탄이 됩니다.

❌ AI-Assisted

“이 함수만 짜줘” — 컨텍스트가 단절되어 생산성 향상이 미미하고, 낡은 비효율을 오히려 강화합니다.

✅ AI-DLC

전 과정에 AI가 참여하되, 사람이 컨텍스트와 가드레일을 설계합니다. 방법론의 핵심은 이 균형입니다.

한 문장 요약: 실행은 AI에게 통째로 넘기고, 사람은 결정과 검증만 한다 — 단, 폭주하지 않도록 관문을 세우고, 결정과 맥락을 파일로 남긴다.

PLAN · ASK · DEFER — AI-DLC의 심장 패턴
  1. 나

    Using AI-DLC, 고객 문의 검색 기능을 추가하자.

  2. AI · 계획한다

    요구사항 확인 → 설계 → 구현 → 테스트 순서로 진행하겠습니다.

  3. AI · 질문한다

    먼저 확인이 필요합니다. Q1. 검색 대상은? (A) 제목만 (B) 본문 포함 · Q2. 정렬은? (A) 최신순 (B) 관련도순

  4. 나

    Q1은 B, Q2는 A.

  5. AI · 미룬다

    답변 기반 실행 계획입니다. 승인하시면 구현을 시작합니다 — Continue / Request Changes?이 승인이 있기 전까지 AI는 코드를 한 줄도 작성하지 않습니다. 이 패턴이 SDLC의 모든 활동에서 빠르게 반복됩니다.

요청 A · “오타 고쳐줘”

5단계, 몇 분 컷

Workspace 확인 → 요구 확인(얕게) → 계획 → 코드 생성 → 빌드·테스트. 유저 스토리·설계 단계는 “버그 수정”이라 스킵하되, 스킵 결정조차 사람에게 보고하고 승인받습니다.

질문 1–2개 + 승인 2번
요청 B · “결제 기능 만들어줘”

12단계 풀코스, 하루 이상

페르소나·유저 스토리, 신규 컴포넌트 설계, 유닛 분해(결제 요청·승인 콜백·환불), 유닛마다 기능 설계 + NFR(보안·동시성) + 인프라 설계까지 전부 실행합니다.

질문 수십 개 + 승인 게이트 다수

적응형 지능: 같은 규칙 파일인데 요청의 위험도에 따라 프로세스가 고무줄처럼 늘고 줄어듭니다. 애매하면 “포함”이 기본값입니다.

aidlc-state.md

어디까지 왔는지 기록하는 상태 파일. 세션이 끊겨도 다음 세션이 이 파일을 읽고 이어서 재개합니다.

audit.md

모든 입력과 결정을 시간순으로만 추가(append-only)하는 감사 로그. “이 코드는 누가 언제 승인했나”에 답합니다.

승인 게이트

“DO NOT PROCEED until user confirms” — 규칙 원문에 16회 이상 반복되는 문장. 선택지는 Continue / Request Changes 2택뿐입니다.

  • 안 하면: 언젠가 곤란해짐 (천천히 아픔)
  • 그래서 항상 뒤로 미뤄짐

다음 단계 AI의 연료

독자는 AI — 다음 세션의 에이전트

  • 목적: AI의 작업 기억 — 채팅은 세션이 끝나면 증발
  • 안 하면: 당장 다음 세션이 바보가 됨 (즉시 아픔)

관점 전환: 문서는 워크플로의 부산물이 아니라 연료입니다. AI-DLC에서 문서화는 목적이 아니라 수단입니다.

QUIZ

“AWS가 주장하는 10~15배 생산성 — 그대로 믿어도 될까요?”

절반만 믿으세요. 실측 사례는 있습니다 — Amazon Bedrock 추론 엔진 재구축은 “엔지니어 40명 × 1년” 견적을 6명이 76일 만에 끝냈습니다. 하지만 자사 도구 홍보 맥락의 자사 사례이고, 측정 기준(코드 줄 수? 기능 수?)도 모호합니다. 숫자는 참고만 하고, 우리 조직의 저위험 파일럿으로 직접 측정하는 것이 정답입니다.

REAL STORY🔍

이미 하고 있었습니다 — 어느 팀의 실화

사내의 한 팀이 LLM 기반 테스트 실패 분석 서비스를 자기 방식대로 개발한 뒤, AI-DLC 렌즈로 되돌아봤습니다. 요구사항 명세 → 기능별 설계 문서(FR/NFR/결정 기록) → Phase별 체크박스 TODO → “회귀 0 확인” 게이트 → 운영 피드백의 문서화까지 — 의도하지 않았는데 이미 절반 이상을 실천하고 있었습니다.

부족했던 것은 산출물이 아니라 결정적 장치였습니다 — 흩어진 결정 기록의 시간순 일원화(audit), 프로젝트 전역 상태 파일(state), “설계 승인 전 구현 금지”의 명문화(gate). 즉 AI-DLC는 잘 굴러가는 AI 협업이 자연히 수렴하는 형태를 AWS가 규칙으로 표준화한 것입니다. 그래서 도입은 갈아엎기가 아니라, 부족한 장치만 골라 설치하는 일입니다. 새 프로젝트라면 첫날부터 통째로 설치하는 쪽이 정답입니다.

내일부터 바꿀 세 가지: AI-DLC의 조언은 “문서를 더 써라”가 아니라 “질문 먼저, 승인 먼저를 규칙으로 박아라”입니다.

① 질문 먼저

“일단 만들어줘” 대신 “구현 전에 모호한 점을 질문으로 먼저 줘” — 프로젝트 중반에 터지던 “그런 뜻이 아니었는데”를 첫날로 앞당깁니다.

② 승인 먼저

“계획·설계 승인 전 코드 작성 금지”를 팀 규칙 파일(CLAUDE.md 등)에 명문화합니다. 관문이 없으면 폭주, 실행을 안 맡기면 굼뜸 — 그 사이의 균형점입니다.

③ 파일로 남기기

질문의 답·설계 결정·진행 상태를 채팅에 흘리지 말고 저장소의 md 파일에 쌓아, 다음 세션이 읽고 이어서 일하게 합니다.

📎

MINI WORKSHOP

Given–When–Then 요구사항 빌더

좋은 요구사항의 8가지 조건 (ISO/IEC/IEEE 29148)

필요성정말 있어야 하는 요구인가? 명확성누가 읽어도 한 가지로 읽히는가? 완전성예외와 경계가 빠지지 않았는가? 일관성다른 요구와 충돌하지 않는가? 실현가능성지금 기술·비용으로 가능한가? 단일성한 문장이 하나만 말하는가? 검증가능성합격·불합격을 판정할 수 있는가? 추적가능성출처와 테스트로 연결되는가?

여덟 개 중 가장 자주 무너지는 것은 검증가능성입니다. 테스터가 합격과 불합격을 판정할 수 없다면, 아직 좋은 요구사항이 아닙니다.

07 / VERIFICATION & VALIDATION
