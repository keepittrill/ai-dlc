아닙니다. 문법을 직접 타이핑하는 비중은 줄지만, 문제정의·시스템 사고·요구사항·품질판단·보안과 검증 역량은 오히려 더 중요해집니다. 신입 100명이 만든 결과물을 검토·승인할 시니어의 일이 늘어나는 것과 같습니다.

PATH A + 5338 + AI RMF + 42001
📎

Copilot에 적용하면 — 이 서비스는 LLM이 들어가므로 PATH B입니다. 12207·29148로 생명주기와 요구사항의 뼈대를 잡고, 5338로 모델 평가·드리프트 관리 같은 AI 고유 활동을 더하고, 42001로 “환불 판단은 반드시 사람이 한다”를 조직의 공식 규칙으로 못 박습니다. 표준은 암기 대상이 아니라 빠뜨린 것을 찾아주는 체크리스트입니다.

05 / REQUIREMENTS

PROMPT IS NOT A SPECIFICATION

AI에게 말을 잘하는 것보다
완료를 정의하는 것.

📎

워크숍 시작 — 아래의 나쁜 프롬프트는 Copilot 첫 회의에서 실제로 나올 법한 요청입니다. 가운데 버튼을 눌러 검증 가능한 명세로 바뀌는 과정을 확인하고, 이어서 여러분의 요구사항도 직접 만들어 보세요.

BAD PROMPT
“고객 문의를 AI가 알아서 잘 답하게 만들어줘.”
사용자?범위?데이터?실패 기준?보안?
VERIFIABLE SPEC
  • 목적 승인된 지식문서에 근거해 1차 답변 제공
  • 범위 배송·환불·계정 문의만 자동 응답
  • 안전 결제·법률·위협 표현은 상담원에게 100% 이관
  • 품질 근거 표시율 ≥ 98%, PII 노출 0건
  • 성능 정상부하에서 p95 응답시간 3초 이내
  • 증거 골든셋·보안테스트·운영로그로 검증
※ 수치는 세미나용 예시이며 서비스 위험도에 맞게 합의해야 합니다.
MINI WORKSHOP

Given–When–Then 요구사항 빌더

좋은 요구사항의 8가지 조건 (ISO/IEC/IEEE 29148)

필요성정말 있어야 하는 요구인가? 명확성누가 읽어도 한 가지로 읽히는가? 완전성예외와 경계가 빠지지 않았는가? 일관성다른 요구와 충돌하지 않는가? 실현가능성지금 기술·비용으로 가능한가? 단일성한 문장이 하나만 말하는가? 검증가능성합격·불합격을 판정할 수 있는가? 추적가능성출처와 테스트로 연결되는가?

여덟 개 중 가장 자주 무너지는 것은 검증가능성입니다. 테스터가 합격과 불합격을 판정할 수 없다면, 아직 좋은 요구사항이 아닙니다.

06 / VERIFICATION & VALIDATION

EVIDENCE, NOT CONFIDENCE

“AI가 테스트했습니다”가 아니라
증거가 통과해야 합니다.

이 장의 핵심은 단 하나 — ‘믿음’과 ‘증거’를 구분하는 것입니다. 요리에 비유하면 Verification은 “레시피대로 만들었나”, Validation은 “손님이 맛있다고 하나”입니다.

Verification 예시

승인된 요구사항이 코드·설정·테스트에 빠짐없이 반영되었는지 확인합니다.

📎

Copilot에 적용하면 — Verification은 “환불 문의는 100% 상담원 이관”이 코드와 테스트에 실제로 존재하는지 확인하는 일입니다. 그런데 실제 상담원이 써 보니, 이관된 문의에 대화 맥락이 없어서 고객에게 처음부터 다시 물어야 한다면? 명세대로 만들었어도(V1 통과) 필요한 시스템이 아닐 수 있습니다(V2 실패). 그래서 둘 다 필요합니다.

QUIZ

“AI가 ‘모든 테스트를 통과했습니다’라고 보고하면, 검증은 끝난 걸까요?”

아직입니다. AI의 보고는 ‘주장’이지 ‘증거’가 아닙니다. 어떤 테스트를 어떤 입력으로 실행했고, 실제 출력·로그·커버리지가 무엇인지 재현 가능한 기록으로 확인해야 합니다. AI는 존재하지 않는 테스트를 “통과했다”고 자신 있게 말하기도 합니다.
