한눈에

코드 리뷰는 버그를 잡는 마지막 관문이자, 팀의 설계 기준을 전파하는 학습 통로입니다. 이 문서는 리뷰어와 작성자 모두가 지킬 최소 규약을 정의합니다.

개요

모든 변경은 최소 1명의 리뷰 승인 후 병합합니다. 리뷰의 목표는 "완벽한 코드"가 아니라 메인 브랜치의 건강을 지키는 것입니다. 흠집을 모두 없애기보다, 되돌리기 어려운 실수를 막는 데 집중합니다.

리뷰는 사람을 심사하는 자리가 아니라, 코드를 함께 더 낫게 만드는 자리다.

리뷰의 목적

리뷰가 답해야 하는 질문은 네 가지입니다. 이 순서대로 무게를 둡니다.

① 정확성의도한 대로 동작하고, 엣지케이스가 깨지지 않는가
② 설계변경이 시스템의 결을 따르고, 나중에 진화 가능한가
③ 가독성6개월 뒤의 내가 읽어도 이해되는가
④ 안전성테스트·로깅·롤백이 갖춰졌는가
📝

스타일·포매팅은 리뷰의 대상이 아닙니다. 린터와 포매터에 위임하고, 사람은 정확성·설계에 집중합니다.

리뷰어 체크리스트

아래를 위에서 아래로 훑습니다. 상위 항목에서 막히면 하위는 볼 필요가 없습니다.

정확성

  • 변경이 PR 설명의 의도와 일치하는가 필수
  • 경계값·빈 입력·동시성·실패 경로가 처리되는가 필수
  • 되돌리기 어려운 변경(마이그레이션·삭제)에 안전장치가 있는가 주의

설계

  • 기존 패턴을 따르는가, 아니면 정당한 이유가 문서화됐는가 필수
  • 책임 경계가 새지 않는가(한 모듈이 너무 많이 아는가) 권장
  • 공개 인터페이스 변경이 호환성을 깨지 않는가 필수

테스트

  • 새 동작에 대응하는 테스트가 있는가 필수
  • 테스트가 구현이 아니라 행동을 검증하는가 권장
  • CI가 통과했는가 CI
⚠️
되돌리기 어려운 변경

DB 마이그레이션·데이터 삭제·외부로 나가는 요청은 가장 먼저, 가장 꼼꼼히 봅니다. 이 부분의 실수는 리뷰로만 막을 수 있습니다.

PR 작성자 가이드

좋은 리뷰는 좋은 PR에서 시작합니다. 리뷰어의 시간을 아끼는 것이 작성자의 책임입니다.

  • 작게 — 한 PR = 한 목적. 400줄을 넘기면 쪼개는 걸 우선 고려합니다(문서용 기준선).
  • 설명 — "무엇을/왜"를 본문에. 스크린샷·재현 절차·리스크를 적습니다.
  • 셀프 리뷰 — 올리기 전에 diff를 스스로 한 번 읽고 코멘트를 남깁니다.
markdown
## 무엇을
환불 가능 기간을 7일 → 14일로 확장

## 왜
CS 문의 1위 항목. 정책팀 승인(SPEC-REFUND-14)

## 리스크
- 기존 주문에 소급 적용 안 됨(마이그레이션 없음)
- 부하 영향 없음(읽기 경로 변경 없음)

## 확인
- [x] 단위/계약 테스트 추가
- [x] 스테이징에서 재현 확인

커밋 메시지는 Conventional Commits를 따릅니다. 브랜치는 목적이 드러나게:

git switch -c feat/refund-window-14
git commit -m "feat: extend refund window to 14 days (SPEC-REFUND-14)"

코멘트 작성법

코멘트에 의도 라벨을 붙이면 작성자가 우선순위를 즉시 압니다. 아래 4종을 씁니다.

라벨뜻병합 차단?
blocking:고쳐야 승인예
question:이해가 필요함경우에 따라
suggestion:제안, 선택 사항아니오
nit:사소함(취향)아니오
💡
팁

지적은 코드에, 칭찬은 사람에게. "이 부분 처리 깔끔하네요 👍" 같은 긍정 코멘트도 남기면 리뷰 문화가 오래갑니다.

⛔
하지 말 것

"이건 왜 이렇게 했어요?"처럼 사람을 겨냥하는 표현, 근거 없는 취향 강요, 리뷰를 볼모로 한 리팩터링 요구. 범위 밖 개선은 별도 이슈로 남깁니다.

승인 기준

다음을 모두 만족하면 Approve, 하나라도 막히면 Request changes입니다.

항목기준판정

리스크 변경안전장치·롤백 확인확인

AI 보조 리뷰

AI 리뷰어(자동 코멘트 봇 등)는 리뷰의 1차 필터로 유용하지만, 승인 권한은 사람에게 있습니다.

🤖

AI가 잘 잡는 것: 널 가드 누락, 반복 패턴 이탈, 명백한 엣지케이스. AI가 놓치는 것: 도메인 의도·되돌리기 어려운 결정·조직 맥락. 후자는 반드시 사람이 봅니다.

자세히: AI 리뷰 코멘트를 다루는 법 (펼쳐 보기)
  1. AI 코멘트도 사람 코멘트와 같은 라벨 규칙(blocking/suggestion 등)으로 취급합니다.
  2. 오탐이면 이유를 한 줄로 남기고 resolve — 다음 사람이 같은 판단을 반복하지 않게.
  3. AI가 옳은데 반복적으로 지적한다면, 그건 린트 규칙이나 스펙으로 승격할 신호입니다.

FAQ

리뷰가 며칠째 안 붙어요.

24시간 내 첫 응답을 목표로 합니다(문서용 기준선). 지연되면 리뷰어를 재지정하거나 채널에 핑을 남기세요. 급하면 페어 리뷰로 전환합니다.

의견이 갈리면 누가 결정하나요?

해당 코드의 오너가 최종 결정합니다. 합의가 안 되면 짧은 동기 논의로 전환하고, 결정 사유를 PR이나 ADR에 남깁니다.
