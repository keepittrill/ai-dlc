AI-DLC 운영 가이드

LK 작성 플랫폼 팀 🕒 최종 수정 2026-08-06 ⏱ 읽는 시간 — 버전 v1.0
ai-native ai-dlc engineering guide
ℹ️
이 문서의 목적

AI-DLC(AI Development Life Cycle)를 팀에 도입·운영하기 위한 실무 참조 문서입니다. 발표가 필요하면 세미나 트랙의 해당 세미나를 함께 보세요.

개요

AI-DLC는 사람이 의도·경계·검증을 소유하고, AI가 생성·탐색·반복을 담당하는 개발 생명주기입니다. 핵심은 "AI가 더 많이 만들수록, 누군가는 전체를 봐야 한다"는 통제 원칙입니다.

  • Living Spec — 의도를 살아있는 명세로 유지
  • Evolvable Design — 변경에 강한 설계
  • System-Level Validation — 시스템 수준 검증 게이트
📝

이 문서의 수치·사례는 별도 출처 표기가 없으면 문서용 예시입니다.

역할 경계

가장 흔한 실패는 "누가 무엇을 소유하는가"가 흐려질 때 발생합니다. 아래 경계를 문서·리뷰·CI에서 반복적으로 확인하세요.

사람이 소유의도, 수용 기준, 아키텍처 제약, 최종 승인
AI가 담당초안 생성, 대안 탐색, 리팩터링, 테스트 초안
함께 반복스펙 정련, 엣지케이스, 트레이드오프 결정
활동주체산출물게이트
요구 정의사람 + AILiving Spec리뷰
설계사람 주도ADR리뷰
구현AI 주도diff + 테스트CI 통과
검증사람 승인계약/부하 테스트조건부 GO
⚠️
주의

AI 산출물을 사람이 승인 없이 병합하면 역할 경계가 무너집니다. 승인 게이트를 자동화로 대체하지 마세요.

리빙 스펙

스펙은 문서가 아니라 실행 가능한 계약입니다. 변경 요청 하나를 스펙 → 코드 → 테스트로 추적할 수 있어야 합니다.

gherkin
Feature: 환불 정책
  Scenario: 7일 이내 환불 요청
    Given 주문이 3일 전에 완료되었고
    When 사용자가 전액 환불을 요청하면
    Then 환불이 승인되고 상태는 "REFUNDED" 가 된다

본문에 바로 <pre> 를 써도 doc.js 가 자동으로 복사 버튼을 붙입니다.

git checkout -b feat/refund-window
npm test -- refund
자세히: 스펙 추적 규칙 (펼쳐 보기)

모든 변경은 스펙 ID를 참조합니다. 예: SPEC-REFUND-07 → 커밋 메시지 → 테스트 이름에 동일 ID가 나타나야 합니다.

  1. 스펙에 ID 부여
  2. 브랜치/커밋에 ID 포함
  3. 테스트에 ID 태그

검증 게이트

시스템 수준 검증은 단위 테스트로 대체되지 않습니다. 아래 순서로 게이트를 통과시킵니다.

  1. 단위·통합 테스트 필수
  2. 계약 테스트(Contract) 필수
  3. 부하 테스트(k6 등) 임계값 기준
  4. 사람 최종 승인 수동
💡
팁

부하 테스트 임계값을 스펙에 명시하면, AI가 생성한 구현이 자동으로 그 기준을 목표로 삼습니다.

⛔
하지 말 것

검증 게이트를 "나중에" 미루는 것. 게이트 없는 대량 생성은 기술 부채를 자동화할 뿐입니다.

도입 로드맵

작게 시작해서, 경계를 먼저 세우고, 검증을 자동화한 뒤 확장한다.
단계기간목표
1. 경계 세우기Day 1–30역할 경계 문서화, 파일럿 1개
2. 게이트 자동화Day 31–60계약·부하 테스트 CI 편입
3. 확장Day 61–90팀 전면 적용, 회고 루프
